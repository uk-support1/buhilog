# 第1部：概要・使い方（README.md）

# ぶひろぐ（BuhiLog）仕様書パッケージ

福祉ITパートナーのキャラクター「ぶひお」にちなんだ、困りごと・改善アプローチ・日次記録・傾向の発見を支援する個人向けアプリの開発仕様書。

**最初の実装は Ver.1 の中核機能に限定**。Bearableの一般的な機能は参考にするが、知財上の表現はコピーしない。医療判断はしない。

## ファイル
- `CLAUDE.md` — Claude Codeへの指示、最初の作業は設計レビューのみ
- `REQUIREMENTS.md` — 機能・バージョン別スコープ
- `SCREENS.md` — 画面・画面遷移
- `DATA_DESIGN.md` — データ構造・保存/バックアップ
- `ANALYTICS.md` — 相関分析・統計表示の具体的ルール
- `SAFETY_LEGAL.md` — 医療・個人情報・知財の安全方針
- `DEVELOPMENT_PLAN.md` — 実装順序・受け入れ基準

## Claude Codeに渡す手順
1. ZIPを展開し、独立した新しいプロジェクトフォルダにこれらのファイルを配置する。
2. Claude Codeでそのフォルダを開く。
3. 下記を貼り付ける。

> このフォルダの `CLAUDE.md` と他の6つの仕様書をすべて読み、まずは **Phase 0の設計レビューだけ** を行ってください。コードの実装はまだ始めず、`docs/IMPLEMENTATION_REVIEW.md` に推奨技術、画面・データモデル、分析ロジック、未確定事項、実装順、テスト案とリスクをまとめてください。Bearableの独自のデザインや文面をコピーせず、個人データを外部サービスに送らない構成を前提にしてください。

# 第2部：要件定義（REQUIREMENTS.md）

# ぶひろぐ 要件定義（Ver.1）

## 1. 背景と価値
うつ病などのメンタルヘルス上の困りごとは、睡眠・気分・身体症状・行動・服薬など多数の要因が混在し、本人が改善との関連を見いだしにくい。本人が「何を試し、どう変化したか」を1〜2か月記録し、次に試す工夫や医療者への相談に役立つ材料を見つける。**関連の発見を助ける**のであって、病名の判定や原因の特定、治療指示はしない。

## 2. 対象とゴール
- 初期対象：開発依頼者自身のiPhone中心の個人利用。将来はうつ病等の困りごとを抱える一般ユーザーも想定。
- ゴール：1日1〜2分を目安に記録、1/2/4/8週間の推移と対処法との関連を閲覧、自分で改善策を見直すヒントを得る。
- 非ゴール（Ver.1）：医療機器、医療判断、AI診断、健康データの外部送信、コミュニティ、サブスクリプション、SNS、Appleヘルスケア連携、完全なBearable再現。

## 3. 中核ユーザーフロー
1. 初回：注意事項確認 → 困りごとを1〜5個作る → 困りごとごとに対処法を0〜複数個登録 → 記録開始。
2. 日常：日付を選ぶ → 困りごとの強さ（0=なし〜10=最もつらい）を記録 → 実施したアプローチをチェック → 任意で睡眠時間/ストレス/メモ入力 → 保存。
3. 振り返り：困りごとの推移 → アプローチ実施日・非実施日の分布 → 参考になる関連の候補 → 入力不足や解釈上の注意を確認。
4. 訂正：過去日の記録編集・削除、データ書き出し・復元。

## 4. Ver.1 必須機能（優先度P0）
| ID | 機能 | 受け入れ基準 |
|---|---|---|
| F01 | 困りごとCRUD | 自由な日本語名、説明任意、表示順、アーカイブ可能。重複名・長文を適切に扱う |
| F02 | アプローチCRUD | 名前、対象の困りごと、メモ、実施日。複数症状にひも付けられる |
| F03 | 日次記録 | 日付別・症状別の0〜10評価。未入力を0と扱わない |
| F04 | 実施記録 | アプローチの実施/未実施/不明を区別。後から修正可能 |
| F05 | 基本的生活記録 | 睡眠時間（任意）・ストレス0〜10（任意）・自由メモ（任意） |
| F06 | 記録一覧・編集 | カレンダー/日付順一覧から過去の入力を再編集・削除可能 |
| F07 | 症状推移のグラフ | 日・週単位で可視化、欠損は線で勝手につながず明示 |
| F08 | 基礎比較分析 | 実施日・非実施日ごとの症状スコア平均・差・件数を表示。因果を断定しない |
| F09 | 分析データ不足表示 | 比較可能日数が少なければ「判断材料不足」。閾値は分析仕様に従う |
| F10 | ローカル保存 | 再起動後も記録が残る、データ消失対策を案内 |
| F11 | エクスポート/インポート | JSONバックアップの出力、検証付き復元、CSV書き出し |
| F12 | プライバシー | 外部送信なし。簡潔なデータ取扱いの説明。全件削除可能 |
| F13 | モバイルUI | iPhoneの縦画面で主要操作が成立。日本語・読みやすい文字 |

## 5. 推奨（P1、余力があればVer.1.1）
- 目標：1日1分で済む「かんたん記録」。昨日の内容のコピーは誤記を誘発しない方式に。
- 頓服を含む服薬記録（薬名・予定/実際・用量は任意）を、処方内容の評価と切り離して登録する。副作用・効果の自動判定は行わない。
- 複数回/日の記録（朝・昼・夜）と症状の時間差を分ける。
- エクスポート結果を医師への相談用にまとめる簡易レポート。
- 任意の通知と通知無効化。記録を逃した日を責めない。
- キャラクターを複数のオリジナル候補から選べ、名前と外見を後から変更できる。福祉ITパートナーの「ぶひお」は、権利者側で使用が許可された素材があるときのみ採用。画像未提供時はオリジナル仮キャラ/プレースホルダー。

## 6. 将来バージョン
### Ver.2
- 改善アプローチの目標・実験：開始日/終了日、実行頻度、評価対象、実験前後の推移、予備期間、複数要因の重なり確認。
- より慎重な統計表示：曜日や睡眠等で条件分け、変化量、信頼度ではなく不確実性の説明、十分な入力件数。
- 分析期間指定、欠損・例外日の扱い、週/月レポート、CSVインポート。

### Ver.3以降
- 睡眠・気分・痛み・活動・栄養等の柔軟なトラッキング、Appleヘルスケア連携（技術・権限・審査を別途検証）、カスタマイズ、キャラクター強化、通知。
- クラウド同期・多端末・一般公開・課金・AI自然言語説明は、費用・セキュリティ・法務レビュー後に別プロジェクトとして評価。

## 7. UX原則
- 症状の多い日でも短時間で操作できる。強制入力項目を増やさない。
- やる気や気分を「良い/悪い」で評価しない。責める表現、連続記録の過度な圧力、断定的な励ましを避ける。
- 「改善」が無いときも、記録できた事実と観察状況をニュートラルに示す。
- 数値は「スコアの平均差」か「割合」かを明確にし、意味不明な独自%を出さない。

## 8. 今回の参考アプリ
Bearable（ベアラブル）の画面を参考として、初期設定、症状の自由追加、服薬、生活習慣、分析画面、グラフ、レポート、キャラクター選択の必要性を検討。画面の忠実複製はしない。

## 9. 未確定事項
アプリの正式ロゴ、実物の「ぶひお」素材の使用条件、端末構成、バックアップ先、通知要否、サーバー導入は初回設計レビューで確認する。確認前はオフラインPWA・端末内保存を仮定。

- 初回：S00 → S01 → S02。
- 日次：S02 で保存 → S05 または S06。
- 管理：S02 → S03/S04 → S02。
- 分析：S02 → S06 → S07 → S06。
- データ操作：S02 → S08。

## ナビゲーション案
下部タブは3つ：**記録／ふりかえり／設定**。困りごと・アプローチ管理は記録画面から開く。Bearableのメニュー配置をそのまま模写しない。

## S02 詳細
1. 日付・保存結果・「あとから直せる」案内。
2. 困りごと別カード：「右肩の痛み」等。0〜10の評価、未入力状態、任意メモ。
3. 実施したアプローチを切り替える。未実施を入力したか、単に未回答かを分ける。
4. 任意の睡眠時間、ストレス、自由メモ。
5. 明示的な「保存」ボタンと保存確認。誤操作防止。
6. 登録件数が増えても折りたたみ・表示順で扱いやすくする。

## S06/S07 詳細
- 期間と困りごとを選択。日別折れ線/点描。平均線は必要なときだけ。
- アプローチ単位の比較は、評価の小さいほうが症状が軽いことを明記。
- 凡例：「実施した日」「実施しなかった日」「未回答」。分析対象日数と除外理由を表示。
- アプローチの分析結果は「観察された差」であり「効いた確率」「原因」ではない。
- 0件や少数件でも壊れない画面。分析できない理由を説明する。

## アクセシビリティ・品質
- タッチ領域44px程度以上。色だけで意味を区別しない。
- VoiceOver向けラベル、文字拡大、明暗コントラスト。
- 日時・タイムゾーンは端末ローカル日付を基準に扱い、日付跨ぎで記録が移動しない。
- 通信がなくても日次記録・分析が動く。

## キャラクター（将来）
複数のオリジナルキャラクターから選択可能、命名・変更可能。初期段階では日次記録の邪魔をしない。過度なゲーミフィケーションは避ける。

# 第4部：データ設計（DATA_DESIGN.md）

# ぶひろぐ データ設計（初期案）

## 方針
- オフライン優先、端末内に保存。推奨：IndexedDB（例：Dexie）。localStorage単独で重要記録を保存しない。
- 安全なマイグレーション、入力検証、JSONバックアップ、データ喪失対策を実装。
- **空欄/nullは症状スコア0とは別**。アプローチの未回答は未実施とは別。
- 集計は表示のたびに元データから再計算し、派生値を正規データとして保存しない。

## 概念モデル
### Problem（困りごと）
`id`, `name`, `description?`, `unit="severity_0_10"`, `order`, `archivedAt?`, `createdAt`, `updatedAt`

### Approach（アプローチ）
`id`, `name`, `notes?`, `linkedProblemIds[]`, `archivedAt?`, `createdAt`, `updatedAt`

### DailyEntry（日次記録）
`id`, `localDate`（YYYY-MM-DD）、`problemRatings`（problemId → 0〜10 or null）、`approachStatuses`（approachId → "done"|"not_done"|"unknown"）、`sleepHours?`、`stressRating?`（0〜10）、`note?`、`createdAt`, `updatedAt`

### AppSettings
`schemaVersion`, `onboardingCompleted`, `preferredProblemId?`, `reminderEnabled=false`, `characterId?`, `characterName?`

## 制約と設計判断
- `DailyEntry.localDate` は一意。複数回更新で同日の記録を上書きしないようトランザクション化。
- スコアは整数0〜10。保存前に型・範囲検証。日付文字列とUTCタイムスタンプを分離する。
- 先に登録した症状を後でアーカイブしても、過去の記録・分析結果は残す。
- 薬はVer.1 P0に含めない。追加時には `Medication`（名称、予定等）と `MedicationIntake`（実際の服用）を分け、個人の治療変更提案はしない。
- 改名・アーカイブした項目についてJSONからの復元後も参照整合性を維持。
- 日次日付を `new Date().toISOString().slice(0,10)` で求めない（UTC日付ズレが生じる）。

## バックアップ・移行
- JSON：`formatVersion`, `exportedAt`, `problems`, `approaches`, `dailyEntries`, `settings` を含む。
- インポートは先にスキーマと参照整合性を検証し、何件取り込むかをプレビュー。既存データ上書きは二重確認。
- CSV：日付・症状ID/表示名・スコア・アプローチ実施状況等の読める形式。自由記述の改行・カンマ・式インジェクションに注意。
- iOSでPWAのデータが端末/ブラウザ設定により消去されうることを明示し、定期エクスポートを案内。一般公開時はデータ保護方式を再設計。

## セキュリティ
- 埋め込みのAPIキーや資格情報を禁止。第三者Analytics/広告SDK無し。
- Content Security Policy、依存関係の更新、XSS対策。メモはテキストとして表示しHTMLとして解釈しない。
- UIでデータ保持・保存先・削除方法を説明。端末共有やバックアップファイルの取り扱い注意を表示。

# 第5部：分析仕様（ANALYTICS.md）

# ぶひろぐ 分析仕様（Ver.1）

## 中心原則
- これは個人の記録を探索するための**記述統計**であり、介入の治療効果や因果関係を証明しない。
- `症状スコア0 = 症状なし`、`10 = 最もつらい`。欠損/nullを0扱いしない。
- 観察した関連を「効果」「成功率」「原因」「副作用の確定」などと呼ばない。
- 結果に `観察期間` `評価がある日数` `実施日数` `非実施日数` `欠損件数` を添える。

## A01 症状の時系列
入力：problemId、期間（直近7/14/28/56日、必要に応じ手動指定はVer.2）。
出力：日別スコアの点、週ごとの平均、スコアが入力された日数、欠損日数。欠損値の補間はしない。週次平均は観測値のみで算出し分母を表示。

## A02 アプローチ実施有無の比較
入力：problemId、approachId、期間。
比較集団：`done` の日 / `not_done` の日。`unknown` は集計除外。両群とも当該症状の数値記録がある日のみ。
算出：
- `meanDone = sum(rating on done days)/nDone`
- `meanNotDone = sum(rating on not_done days)/nNotDone`
- `difference = meanDone - meanNotDone`（マイナスの場合、実施日のほうが症状が軽い**傾向**）
- 各群の標本数、標準偏差（計算可能な場合）、参考範囲。
- 当日比較は同時性があるため方向性を示さない。「対処したのは症状が重かったから」の逆因果にも注意。

## データ量とラベル
- どちらかが0日：比較不可。単純な傾向グラフのみ。
- いずれか1〜4日：判断材料が少ないため差の値を参考表示にとどめ、目立つ評価やランキングを出さない。
- 両群5日以上：探索的な平均差を表示。ただし「確かな効果」等の表現は禁止。
- 目安の閾値は製品の医学的妥当性が検証された基準ではなく、表示上の安全策。統計的有意性とみなさない。
- 比較の日数、症状の重症度、曜日、睡眠、複数の行動などに偏りが生じる可能性を常に説明。

## 表示の文章例
- 「直近28日間のうち、ストレッチを実施した10日の平均は3.4、実施しなかった12日の平均は5.1でした。差は-1.7ポイントです。」
- 「この差は記録された日との関連を示すだけで、ストレッチが原因で改善したとは断定できません。」
- 「睡眠やその日の活動など、記録していない要因も影響する可能性があります。」
- データ不足：「比較できる記録がまだ十分ではありません。無理のない範囲で記録を続けてみてください。」

## 分析上の禁止
- 服薬内容から「この薬が原因」「薬をやめるべき」と結論する。
- 確率として解釈できない数値を「改善確率84%」等で表示する。
- 実施日と非実施日の件数が極端に異なるのに、それを隠してランキングする。
- 行動の同時実施、症状に応じて行動を選ぶバイアス、長期トレンドを無視して「効果」とする。
- 分析結果に基づく独断の治療指示を行う。

## テストデータと自動テスト
- 欠損日、0点、10点、同日編集、集団0件、両群1件、同点、負の差・正の差、全日未回答、アーカイブ済み要因、日付境界。
- 固定フィクスチャ例：実施2日=[2,4] 平均3、非実施2日=[5,7] 平均6、差=-3。表示はデータ不足と明記。
- 表示値と入力件数の整合性、エクスポート→インポート後に同じ集計となることを確認。

## Ver.2 拡張
- 介入開始前後の比較・遅延効果、曜日・睡眠を考慮した層別、過剰な多重比較への対処、可視化による不確実性の表現。
- 記録前に検証したい仮説を固定し、試した期間と中止条件を記録する。ただし健康に害があり得る行動の実験を推奨しない。

# ぶひろぐ 安全・規制・知的財産・プライバシー

> 本書は開発のための暫定的な安全設計方針であり、法的な適法性の保証ではない。一般公開時は日本の最新法令、厚労省・PMDAのプログラム医療機器該当性、個人情報保護法、利用規約等を別途精査する。

## 1. 医療との境界
- Ver.1の目的はセルフモニタリングと振り返り。病気の診断、治療方針の決定、薬の増減・中止・代替、個人の医学的予後予測は対象外。
- 分析は観察された傾向に限定。強さを伴う症状・新しい危険な症状等はアプリで判断させず医療者へ相談する一般的な案内にとどめる。
- 注意書きは必要だが、実際の機能や広告が診断/治療を目的とすれば注意書きだけでは規制は回避できない。
- 将来、AIによる個別アドバイス、薬剤効果予測、疾病管理・治療支援を追加する場合は、実装前に専門家とSaMD（プログラム医療機器）該当性を再評価。

## 2. 表現チェック
**可**：「直近28日間では睡眠が長い日にスコアが低い傾向がありました（15日分の記録）」
**不可**：「睡眠不足があなたのうつ病の原因です」
**可**：「実施日平均4.2、非実施日平均5.1」
**不可**：「この対処で治ります」「処方薬を減らしてください」
- 孤立した高リスクな自由記述に機械的な断定回答を返さない。Ver.1で自由文AI相談は提供しない。

## 3. プライバシー
- 精神疾患の病歴等は要配慮個人情報に該当し得る。公開・クラウド化の際は本人同意、利用目的、委託先・越境移転、第三者提供、安全管理、削除対応などを法務確認。
- 試作版でも実データをGitリポジトリ、バグ報告、スクリーンショット、ログ、外部AIプロンプトに混入させない。
- ローカル保存においても端末の破損・ブラウザデータ削除の危険を伝え、バックアップを提供する。
- 外部計測、広告、クラッシュレポート等は初期版に入れない。機微情報をURLクエリに付けない。

## 4. Bearableとの知的財産
- 一般的な機能（症状の記録、平均の算出、時系列グラフ等）は、自前のコードと独自の表現で実装する。
- BearableのUI素材、文字、キャラクター、スクリーンショットの配布、ソースコード、ブランド名、独自レイアウトの直接複製をしない。

# ぶひろぐ — Claude Code 開発指示

## 目的
「ぶひろぐ（BuhiLog）」は、日々の困りごと・症状、試した対処法、生活要因を少ない負担で記録し、個人内の時間的な関連と変化を可視化するセルフモニタリングアプリ。福祉ITパートナーのキャラクター「ぶひお」に由来する。最初は開発依頼者本人が使用する個人向け試作版。商品化や公開は現時点で対象外。

## 必ず守ること
1. **実装開始前に**全仕様書を読み、矛盾・決定待ち・実装順・技術案を `docs/IMPLEMENTATION_REVIEW.md` に整理して提示する。コード着手は依頼者が設計を確認した後。過剰な質問は避け、合理的な仮定を明記する。

3. 医学的診断、因果関係の断定、薬の変更・中止・増減の指示を出さない。分析結果は観察された**関連**であり治療効果の証明ではない。免責表示だけで安全性を満たしたことにしない。
4. **個人の健康情報を最優先で保護**。Ver.1はローカル保存を基本とし、データを外部AI・分析基盤・広告SDKに送信しない。同期やクラウド化は別途明示的に設計・承認。
5. モバイル優先、日本語UI、少ない入力回数、データの修正・削除・エクスポートができること。
6. 小さく実装し、テストを実行し、状態を説明する。既存のクライアント案件・HP制作リポジトリと混在させない。
7. 推測による相関を「有効」と表現しない。サンプル数・欠損・交絡の限界を表示する。データ不足なら不足と説明する。
8. データ構造・分析ロジックとUIを分離し、将来の機能拡張に備える。

## 用語
